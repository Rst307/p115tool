# 分享失效后的重新归档

## 手动与自动入口

`POST /share/repair`，管理密钥认证，body `{"media_id":1}`。先尝试重新定位并深度验证原分享；能够恢复就不创建新分享。

`auto_repair_share`默认false。开启且分享后端启用后，健康检查发现分享校验失败时，可以调用同一修复流程。普通metadata检查只对已经检测出的异常修复；不会声称它证明了直链可播放。深度检查包含Range探测。

## 来源和验证

先确认认证可用，再使用仍保留且名称/大小/SHA1相符的个人盘源。若无有效源，可使用READY缓存，但须验证缓存目录归属、文件身份及父目录，并更新播放保护租约。

来源均不可验证、目录身份变化、已有未完成整理或源删除检查点时拒绝。不会为了修复删除源文件或缓存，也不会变更播放token/虚拟路径。

## 检查点和原子切换

重新创建前保存 `settings.share_repair:<id>` 意图，包含媒体身份与选定源ID。原分享映射保留；创建成功后立即保存新分享标识，再更新长期有效期、读取匹配文件、获取安全直链、探测Range并验证STRM。

新分享全部通过后，同一SQLite事务替换后端映射、更新READY并清理修复意图。任何前置步骤失败都会保留旧映射及检查点。范围验证/持久化后的失败可再次执行repair，复用已记录的分享，不再create_share。

创建超时且没有保存返回码时，不盲目重建。人工找到该操作已有的分享结果后接入：

```http
POST /share/repair/attach
{"media_id":1,"share_code":"existingcode","receive_code":"abcd"}
```

必须已有修复意图。已经记录的返回码不能静默换成另一分享；所接入分享仍须通过完整媒体身份、长期有效期和Range验证，且不产生源删除操作。

## 分组边界

单成员入口仍拒绝分组成员，避免拆组；电影/季分享使用整组入口：

```http
POST /share/group/repair
{"group_id":1}
```

原组必须READY、成员仍属于同一不可变快照，名称/大小/SHA1及当前后端与快照匹配。所有成员须有可验证的保留源或READY自有缓存；缺任一成员时不会创建替代分享。来源可以混合普通源和缓存，但源身份不得重复。

先保存 `settings.group_repair:<id>` 意图，再以全部源ID创建一个分享。每个成员完成长期有效期、元数据、URL、Range及STRM验证后，一次SQLite事务切换所有成员与组的分享映射，不会先切换已经成功的一集。中间失败保留全部旧映射。缓存和源不删除，token、虚拟路径及成员快照不改变。

创建超时没有返回码时，通过专属组修复接入（不是原始归档的 `/share/group/attach`）：

```http
POST /share/group/repair/attach
{"group_id":1,"share_code":"existingcode","receive_code":"abcd"}
```

必须已有组修复意图；组/成员身份变化、原归档未完成、不确定删除或独立修复冲突均拒绝。已记录码的验证失败可以再次执行group/repair，复用同一分享。`repair_pending`仅表示有修复检查点，不返回分享码/密码。

启用 `auto_repair_share` 后，健康检查发现分组成员异常会尝试整组修复，而不是绕过屏障做单集重建。整组验证可能超过一次health_batch的成员数，是保持不可拆分屏障的必要范围；只有可用源/缓存齐备才能自动推进。

## 验证边界

`test_share_repair.py`覆盖非分组修复。`test_group_repair.py`覆盖全部成员一次创建、缺源拦截、单成员Range失败保留全组、创建超时重启/接入、事务中断全组回滚、全缓存重新归档、原检查点/成员身份保护、健康自动路由、管理鉴权和检查点脱敏。远端行为由可控客户端模拟；真实分享审核、长期参数及删除后可用性仍需授权账户联调。
